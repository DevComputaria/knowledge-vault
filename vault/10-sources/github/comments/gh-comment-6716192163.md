## 1. *Pro .NET Memory Management*: compreender o que acontece com a memória

**Autores da segunda edição:** Konrad Kokosa, Christophe Nasarre e Kevin Gosse.  
**Referência:** [página da segunda edição na editora](https://link.springer.com/book/10.1007/979-8-8688-0453-3).

### Por que estudar este livro?

É a referência mais aprofundada desta lista para entender **como o gerenciamento de memória influencia desempenho, escalabilidade e estabilidade**.

A vantagem não é apenas aprender a evitar alocações. É desenvolver condições para responder a perguntas como:

- Por que a memória do processo cresce mesmo com o GC funcionando?
- Por que uma aplicação que aloca pouco pode manter muita memória ocupada?
- Por que determinados objetos sobrevivem a várias coletas?
- Quando reutilizar buffers ajuda e quando apenas aumenta a memória retida?
- Por que uma mudança diminui as alocações, mas não melhora a latência?

### 1.1. Primeiro foco: alocação, sobrevivência e retenção

Esses três conceitos precisam ser separados.

**Alocação** é a criação de espaço para novos objetos. Uma aplicação pode criar muitos objetos temporários por segundo.

**Sobrevivência** ocorre quando objetos continuam alcançáveis durante uma coleta e, portanto, não podem ser descartados.

**Retenção** é a manutenção desses objetos por referências existentes — por exemplo, em caches, campos estáticos, coleções ou assinaturas de eventos.

Considere:

```csharp
public static class Historico
{
    private static readonly List<byte[]> Itens = new();

    public static void Adicionar()
    {
        Itens.Add(new byte[1024 * 1024]);
    }
}
```

O problema não é o GC “esquecer” de coletar os arrays. A lista estática mantém referências a eles.

Enquanto essas referências permanecerem, os arrays continuam alcançáveis.

**Aprendizado central:** o GC recupera memória de objetos inalcançáveis; ele não decide se um objeto ainda é útil para o negócio.

### 1.2. Segundo foco: gerações e custo das coletas

Estude:

- Gerações 0, 1 e 2.
- Promoção de objetos.
- Small Object Heap e Large Object Heap.
- Compactação e fragmentação.
- Modos de operação do GC.
- Relação entre objetos sobreviventes e trabalho de coleta.

Evite reduzir o assunto à regra “alocar é caro”.

Muitas alocações pequenas têm custo direto baixo. O problema pode aparecer no conjunto:

1. O programa aloca objetos continuamente.
2. O runtime precisa realizar coletas.
3. Parte dos objetos continua viva.
4. O GC precisa percorrer referências e, em determinadas coletas, mover objetos.
5. Esse trabalho consome CPU e pode introduzir pausas.

A frequência e o impacto desse processo dependem da carga, do tamanho do conjunto de objetos vivos, dos limites de memória e da configuração do runtime.

Para uma introdução gratuita antes do livro, consulte [Fundamentos da coleta de lixo — Microsoft Learn](https://learn.microsoft.com/dotnet/standard/garbage-collection/fundamentals).

### 1.3. Terceiro foco: fontes menos evidentes de alocação

Ao ler, procure relacionar o conteúdo a construções do C#:

- Boxing de tipos por valor.
- Closures que capturam variáveis.
- Criação de arrays temporários.
- Operações de strings.
- Materialização de consultas com `ToList()` e `ToArray()`.
- Certos padrões com delegates, iteradores e código assíncrono.

Essas construções **não são necessariamente problemas**. A pergunta relevante é:

> Elas aparecem em um caminho executado com frequência suficiente para afetar uma métrica importante?

Uma alocação em uma rotina administrativa executada diariamente tem relevância diferente da mesma alocação em uma operação chamada milhões de vezes.

### Exercício recomendado

Compare dois cenários:

1. Criar objetos e descartá-los rapidamente.
2. Criar os mesmos objetos e manter uma parte em uma coleção.

Observe separadamente:

- Bytes alocados por segundo.
- Tamanho do heap gerenciado.
- Frequência de coleta.
- Objetos que permanecem vivos.
- Consumo de CPU.
- Latência sob carga.

**O objetivo é perceber que taxa de alocação e memória retida não são a mesma medida.**

## 2. Documentação de `Span<T>` e `Memory<T>`: escrever APIs que evitam cópias desnecessárias

**Referência principal:** [Diretrizes de uso de `Memory<T>` e `Span<T>` — Microsoft Learn](https://learn.microsoft.com/en-us/dotnet/standard/memory-and-spans/memory-t-usage-guidelines).

Essa leitura conecta os fundamentos de memória à escrita de código.

### 2.1. O primeiro conceito: visão de memória não é cópia

Um `ReadOnlySpan<char>` pode representar parte de uma string sem criar outra string com aquele conteúdo.

```csharp
using System;
using System.Globalization;

string entrada = "pedido:12345";

ReadOnlySpan<char> numeroTexto =
    entrada.AsSpan("pedido:".Length);

int numero = int.Parse(
    numeroTexto,
    CultureInfo.InvariantCulture);
```

Nesse exemplo:

- A string original já existe.
- `AsSpan` cria uma visão de seus caracteres.
- O recorte não copia os caracteres.
- O parsing não exige uma substring intermediária.

Compare com:

```csharp
string numeroTexto =
    entrada.Substring("pedido:".Length);

int numero = int.Parse(
    numeroTexto,
    CultureInfo.InvariantCulture);
```

Para essa entrada, `Substring` cria uma nova string contendo `"12345"`.

**A diferença importante não é “colocar a string na stack”.** Os caracteres continuam na string original. A economia vem de não criar uma segunda string.

### 2.2. O segundo conceito: representação e armazenamento são coisas diferentes

Ao estudar esses tipos, separe:

1. **Onde estão os dados?**
2. **Qual tipo representa o acesso a esses dados?**
3. **Por quanto tempo esse acesso é válido?**

| Tipo | Função principal | Pode ser campo de classe? | Permite escrita por essa visão? |
|---|---|---:|---:|
| `Span<T>` | Visão de memória com restrições de escape | Não | Sim |
| `ReadOnlySpan<T>` | Visão de leitura com restrições de escape | Não | Não |
| `Memory<T>` | Representação que pode ser armazenada e atravessar operações assíncronas | Sim | Sim, pelo acesso adequado |
| `ReadOnlyMemory<T>` | Representação de leitura que pode ser armazenada | Sim | Não |

Dois cuidados:

- `Memory<T>` é um `struct`: seu uso não implica automaticamente uma nova alocação no heap.
- `ReadOnlySpan<T>` impede escrita **por aquela visão**, mas não torna necessariamente imutável o armazenamento subjacente. Um array ainda pode ser alterado por outra referência.

Também não é correto tratar `Memory<T>` como “sempre mais lento”. O custo depende de como a API é usada e do código gerado.

### 2.3. O terceiro conceito: tempo de vida e operações assíncronas

O ponto essencial é que um `Span<T>` não pode permanecer vivo atravessando um ponto de suspensão como `await`.

Em versões modernas do C#, há usos permitidos de spans dentro de métodos assíncronos, respeitadas as restrições da linguagem. Portanto, a regra absoluta “`Span<T>` nunca pode aparecer em métodos `async`” é excessivamente ampla.

Para representar um buffer durante uma operação assíncrona, `Memory<T>` é normalmente a escolha apropriada:

```csharp
using System;
using System.IO;
using System.Threading;
using System.Threading.Tasks;

static async Task<int> LerAsync(
    Stream origem,
    Memory<byte> destino,
    CancellationToken cancellationToken)
{
    return await origem.ReadAsync(
        destino,
        cancellationToken);
}
```

Esse contrato, porém, exige que o armazenamento continue disponível até a conclusão da operação.

### 2.4. O quarto conceito: propriedade do buffer

A documentação não trata apenas de velocidade. Ela trata de **quem pode usar a memória, por quanto tempo e quem deve liberá-la ou devolvê-la**.

Isso é fundamental com pools:

```csharp
using System;
using System.Buffers;
using System.IO;
using System.Threading;
using System.Threading.Tasks;

static async Task<int> LerComPoolAsync(
    Stream origem,
    CancellationToken cancellationToken)
{
    const int tamanhoSolicitado = 4096;

    byte[] buffer =
        ArrayPool<byte>.Shared.Rent(tamanhoSolicitado);

    try
    {
        int lidos = await origem.ReadAsync(
            buffer.AsMemory(0, tamanhoSolicitado),
            cancellationToken);

        // Processar os primeiros "lidos" bytes aqui,
        // enquanto o buffer ainda pertence a esta operação.

        return lidos;
    }
    finally
    {
        ArrayPool<byte>.Shared.Return(buffer);
    }
}
```

Pontos que merecem atenção:

- O array alugado pode ser maior que o tamanho solicitado.
- Seu conteúdo anterior não deve ser considerado inicializado.
- Só os bytes efetivamente lidos devem ser tratados como entrada válida.
- O buffer não deve ser devolvido enquanto uma operação ainda o utiliza.
- Depois da devolução, nenhuma referência ou visão deve continuar sendo usada.
- Dados sensíveis podem exigir limpeza antes da reutilização.

**Pooling troca parte do custo de alocação por responsabilidades adicionais de ciclo de vida.**

### Exercício recomendado

Implemente um parser simples de uma linha como:

```text
produto=42;quantidade=7;preco=19.90
```

Faça duas versões:

1. Com `Split` e strings intermediárias.
2. Com `ReadOnlySpan<char>` e recortes.

Antes de medir desempenho, garanta a equivalência funcional:

- O que acontece quando falta um campo?
- Qual cultura numérica é utilizada?
- Espaços são permitidos?
- Valores inválidos retornam erro ou lançam exceção?
- Campos repetidos são aceitos?

Uma versão mais rápida que trata entradas de maneira diferente não é uma substituição equivalente.

## 3. *Writing High-Performance .NET Code*: transformar conhecimento em decisões de engenharia

**Autor:** Ben Watson.  
**Referência:** [site oficial do livro](https://www.writinghighperf.net/).

### Como ele complementa o livro de memória?

Enquanto *Pro .NET Memory Management* aprofunda o gerenciamento de memória, o livro de Ben Watson oferece uma perspectiva mais ampla de **medição, funcionamento do CLR e otimização de aplicações**.

A leitura ajuda a mudar a pergunta de:

> “Qual construção de C# é mais rápida?”

para:

> “Qual parte do sistema limita a métrica que preciso melhorar?”

### 3.1. Estabelecer uma meta mensurável

“Melhorar performance” é um objetivo incompleto.

Exemplos mais úteis:

- Reduzir a latência p99 de determinado endpoint.
- Aumentar o throughput sem ampliar o número de instâncias.
- Diminuir o uso de CPU mantendo a mesma carga.
- Reduzir memória retida durante um processamento em lote.
- Melhorar o tempo de inicialização.

Esses objetivos podem entrar em conflito.

Por exemplo:

- Um cache pode reduzir latência, mas aumentar memória.
- Mais paralelismo pode reduzir o tempo de um lote, mas elevar consumo de CPU e contenção.
- Um pool pode reduzir alocações, mas manter buffers grandes residentes.

### 3.2. Separar custo local de impacto global

Suponha que um trecho represente 5% do tempo de uma operação.

Mesmo que ele passe a executar duas vezes mais rápido, a operação completa não ficará duas vezes mais rápida.

Em um modelo simplificado:

\[
T_{\text{novo}} = 0{,}95T + \frac{0{,}05T}{2}
= 0{,}975T
\]

A redução do tempo total será de apenas **2,5%**.

Essa é uma aplicação da lei de Amdahl: o ganho total é limitado pela parcela efetivamente melhorada.

**Lição prática:** priorize o custo dominante antes de investir em micro-otimizações.

### 3.3. Ler recomendações considerando a versão do runtime

Livros preservam princípios importantes, mas detalhes de implementação envelhecem.

Ao encontrar uma recomendação específica, pergunte:

- Ela foi medida em qual versão do .NET?
- O compilador JIT atual já realiza essa otimização?
- Existe uma API mais recente?
- O resultado se mantém em ARM64 e x64?
- A recomendação depende de determinado tamanho de entrada?

Use o livro como base de raciocínio, não como uma lista de regras imutáveis.

### Exercício recomendado

Escolha uma operação real e escreva, antes de alterar o código:

1. **Problema:** qual métrica está inadequada?
2. **Evidência:** quais medições demonstram isso?
3. **Hipótese:** qual mecanismo explica o custo?
4. **Intervenção:** qual mudança testa essa hipótese?
5. **Critério de sucesso:** qual melhoria justificaria adotar a mudança?
6. **Risco:** o que pode piorar?

Esse registro evita confundir preferência de estilo com otimização.

## 4. Blog do .NET: acompanhar o que o runtime já otimiza

**Leitura de referência:** [*Performance Improvements in .NET 8*, de Stephen Toub](https://devblogs.microsoft.com/dotnet/performance-improvements-in-net-8).

Os artigos dessa série são úteis porque conectam:

- Exemplos pequenos.
- Benchmarks.
- Mudanças no runtime e nas bibliotecas.
- Explicações sobre os mecanismos responsáveis pelos ganhos.
- Links para alterações no código-fonte.

### 4.1. O que procurar nesses artigos?

#### JIT e código gerado

Estude exemplos de:

- Inlining.
- Desvirtualização.
- Eliminação de verificações redundantes.
- Otimização de loops.
- Vetorização.
- Otimização guiada por perfil, como Dynamic PGO.

A finalidade não é decorar instruções de assembly. É entender por que duas formas aparentemente semelhantes podem produzir resultados diferentes — e por que isso pode mudar entre versões.

#### Bibliotecas e APIs

Observe melhorias em:

- Strings e busca em texto.
- Coleções.
- LINQ.
- Serialização.
- Operações de entrada e saída.
- Parsing e formatação.

Às vezes, o melhor ganho vem de **atualizar o runtime ou adotar uma API existente**, em vez de manter uma implementação manual complexa.

### 4.2. Como interpretar os números?

Não leia “X vezes mais rápido” como uma promessa para qualquer aplicação.

Verifique:

1. Qual operação foi medida?
2. Qual era o tamanho da entrada?
3. Quais versões foram comparadas?
4. Qual arquitetura de hardware foi usada?
5. A medição considera inicialização ou execução estabilizada?
6. Seu sistema realiza essa operação com frequência relevante?

Um ganho expressivo em uma busca específica pode ter impacto mínimo em um serviço cujo tempo é dominado pelo banco de dados.

### Exercício recomendado

Selecione um benchmark de uma API usada no seu projeto e reproduza-o:

- Nas versões de runtime relevantes.
- Com diferentes tamanhos de entrada.
- Com dados semelhantes aos reais.

Depois, valide o resultado na aplicação. O microbenchmark explica um mecanismo; o teste integrado mostra sua relevância.

## 5. Complemento essencial: documentação do BenchmarkDotNet

Para aproveitar as outras leituras, é necessário medir de forma confiável.

**Referências:**

- [Primeiros passos](https://benchmarkdotnet.org/articles/guides/getting-started.html).
- [Boas práticas](https://benchmarkdotnet.org/articles/guides/good-practices.html).

### O que estudar primeiro?

- `[Benchmark]`: identifica o método medido.
- `Baseline`: define a referência de comparação.
- `[Params]`: permite variar entradas.
- `[MemoryDiagnoser]`: adiciona diagnóstico de alocações gerenciadas.
- Aquecimento e repetições.
- Variabilidade dos resultados.
- Execução em `Release`, sem depurador anexado.

### Exemplo didático

O exemplo abaixo é independente do vídeo:

```csharp
using System.Globalization;
using BenchmarkDotNet.Attributes;
using BenchmarkDotNet.Running;

BenchmarkRunner.Run<ParsingBenchmarks>();

[MemoryDiagnoser]
public class ParsingBenchmarks
{
    private const string Entrada = "pedido:12345";
    private const int InicioNumero = 7;

    [Benchmark(Baseline = true)]
    public int ComSubstring()
    {
        return int.Parse(
            Entrada.Substring(InicioNumero),
            CultureInfo.InvariantCulture);
    }

    [Benchmark]
    public int ComSpan()
    {
        return int.Parse(
            Entrada.AsSpan(InicioNumero),
            CultureInfo.InvariantCulture);
    }
}
```

Execute em um projeto de console com o pacote instalado:

```bash
dotnet add package BenchmarkDotNet
dotnet run -c Release
```

### Como ler o resultado?

| Coluna | Interpretação |
|---|---|
| `Mean` | Tempo médio medido por operação |
| `Error` | Margem estatística reportada para a estimativa |
| `StdDev` | Dispersão dos tempos medidos |
| `Ratio` | Relação com o benchmark de referência |
| `Allocated` | Bytes gerenciados alocados por operação no escopo medido |

A hipótese é que a versão com span elimine a string intermediária. **O ganho de tempo precisa ser medido, não presumido.**

Além disso, `Allocated = 0 B` não significa que a aplicação inteira não usa memória ou não aloca. O resultado se refere ao escopo medido e não representa todos os possíveis custos, como memória nativa ou inicialização fora da medição.

Para aprofundar a metodologia, o próprio projeto recomenda **_Pro .NET Benchmarking_, de Andrey Akinshin**, na [documentação do BenchmarkDotNet](https://benchmarkdotnet.org/).

Para cada técnica estudada, produza três resultados:

1. **Uma explicação:** qual custo ela pretende reduzir?
2. **Um experimento:** em quais condições a melhoria aparece?
3. **Uma limitação:** quando ela não deve ser aplicada?

Exemplo:

> **Técnica:** reutilizar arrays com `ArrayPool<T>`.  
> **Benefício esperado:** reduzir alocações recorrentes de buffers.  
> **Experimento:** comparar alocação direta e reutilização sob uma carga representativa.  
> **Limitações:** buffers retidos pelo pool, custo de limpeza, complexidade de propriedade e risco de uso após devolução.

O problema não é o GC “esquecer” de coletar os arrays. A lista estática mantém referências a eles.

Enquanto essas referências permanecerem, os arrays continuam alcançáveis.

**Aprendizado central:** o GC recupera memória de objetos inalcançáveis; ele não decide se um objeto ainda é útil para o negócio.

### 1.2. Segundo foco: gerações e custo das coletas

Estude:

- Gerações 0, 1 e 2.
- Promoção de objetos.
- Small Object Heap e Large Object Heap.
- Compactação e fragmentação.
- Modos de operação do GC.
- Relação entre objetos sobreviventes e trabalho de coleta.

Evite reduzir o assunto à regra “alocar é caro”.

Muitas alocações pequenas têm custo direto baixo. O problema pode aparecer no conjunto:

1. O programa aloca objetos continuamente.
2. O runtime precisa realizar coletas.
3. Parte dos objetos continua viva.
4. O GC precisa percorrer referências e, em determinadas coletas, mover objetos.
5. Esse trabalho consome CPU e pode introduzir pausas.

A frequência e o impacto desse processo dependem da carga, do tamanho do conjunto de objetos vivos, dos limites de memória e da configuração do runtime.

Para uma introdução gratuita antes do livro, consulte [Fundamentos da coleta de lixo — Microsoft Learn](https://learn.microsoft.com/dotnet/standard/garbage-collection/fundamentals).

### 1.3. Terceiro foco: fontes menos evidentes de alocação

Ao ler, procure relacionar o conteúdo a construções do C#:

- Boxing de tipos por valor.
- Closures que capturam variáveis.
- Criação de arrays temporários.
- Operações de strings.
- Materialização de consultas com `ToList()` e `ToArray()`.
- Certos padrões com delegates, iteradores e código assíncrono.

Essas construções **não são necessariamente problemas**. A pergunta relevante é:

> Elas aparecem em um caminho executado com frequência suficiente para afetar uma métrica importante?

Uma alocação em uma rotina administrativa executada diariamente tem relevância diferente da mesma alocação em uma operação chamada milhões de vezes.

### Exercício recomendado

Compare dois cenários:

1. Criar objetos e descartá-los rapidamente.
2. Criar os mesmos objetos e manter uma parte em uma coleção.

Observe separadamente:

- Bytes alocados por segundo.
- Tamanho do heap gerenciado.
- Frequência de coleta.
- Objetos que permanecem vivos.
- Consumo de CPU.
- Latência sob carga.

**O objetivo é perceber que taxa de alocação e memória retida não são a mesma medida.**

## 2. Documentação de `Span<T>` e `Memory<T>`: escrever APIs que evitam cópias desnecessárias

**Referência principal:** [Diretrizes de uso de `Memory<T>` e `Span<T>` — Microsoft Learn](https://learn.microsoft.com/en-us/dotnet/standard/memory-and-spans/memory-t-usage-guidelines).

Essa leitura conecta os fundamentos de memória à escrita de código.

### 2.1. O primeiro conceito: visão de memória não é cópia

Um `ReadOnlySpan<char>` pode representar parte de uma string sem criar outra string com aquele conteúdo.

```csharp
using System;
using System.Globalization;

string entrada = "pedido:12345";

ReadOnlySpan<char> numeroTexto =
    entrada.AsSpan("pedido:".Length);

int numero = int.Parse(
    numeroTexto,
    CultureInfo.InvariantCulture);
```

Nesse exemplo:

- A string original já existe.
- `AsSpan` cria uma visão de seus caracteres.
- O recorte não copia os caracteres.
- O parsing não exige uma substring intermediária.

Compare com:

```csharp
string numeroTexto =
    entrada.Substring("pedido:".Length);

int numero = int.Parse(
    numeroTexto,
    CultureInfo.InvariantCulture);
```

Para essa entrada, `Substring` cria uma nova string contendo `"12345"`.

**A diferença importante não é “colocar a string na stack”.** Os caracteres continuam na string original. A economia vem de não criar uma segunda string.

### 2.2. O segundo conceito: representação e armazenamento são coisas diferentes

Ao estudar esses tipos, separe:

1. **Onde estão os dados?**
2. **Qual tipo representa o acesso a esses dados?**
3. **Por quanto tempo esse acesso é válido?**

| Tipo | Função principal | Pode ser campo de classe? | Permite escrita por essa visão? |
|---|---|---:|---:|
| `Span<T>` | Visão de memória com restrições de escape | Não | Sim |
| `ReadOnlySpan<T>` | Visão de leitura com restrições de escape | Não | Não |
| `Memory<T>` | Representação que pode ser armazenada e atravessar operações assíncronas | Sim | Sim, pelo acesso adequado |
| `ReadOnlyMemory<T>` | Representação de leitura que pode ser armazenada | Sim | Não |

Dois cuidados:

- `Memory<T>` é um `struct`: seu uso não implica automaticamente uma nova alocação no heap.
- `ReadOnlySpan<T>` impede escrita **por aquela visão**, mas não torna necessariamente imutável o armazenamento subjacente. Um array ainda pode ser alterado por outra referência.

Também não é correto tratar `Memory<T>` como “sempre mais lento”. O custo depende de como a API é usada e do código gerado.

### 2.3. O terceiro conceito: tempo de vida e operações assíncronas

O ponto essencial é que um `Span<T>` não pode permanecer vivo atravessando um ponto de suspensão como `await`.

Em versões modernas do C#, há usos permitidos de spans dentro de métodos assíncronos, respeitadas as restrições da linguagem. Portanto, a regra absoluta “`Span<T>` nunca pode aparecer em métodos `async`” é excessivamente ampla.

Para representar um buffer durante uma operação assíncrona, `Memory<T>` é normalmente a escolha apropriada:

```csharp
using System;
using System.IO;
using System.Threading;
using System.Threading.Tasks;

static async Task<int> LerAsync(
    Stream origem,
    Memory<byte> destino,
    CancellationToken cancellationToken)
{
    return await origem.ReadAsync(
        destino,
        cancellationToken);
}
```

Esse contrato, porém, exige que o armazenamento continue disponível até a conclusão da operação.

### 2.4. O quarto conceito: propriedade do buffer

A documentação não trata apenas de velocidade. Ela trata de **quem pode usar a memória, por quanto tempo e quem deve liberá-la ou devolvê-la**.

Isso é fundamental com pools:

```csharp
using System;
using System.Buffers;
using System.IO;
using System.Threading;
using System.Threading.Tasks;

static async Task<int> LerComPoolAsync(
    Stream origem,
    CancellationToken cancellationToken)
{
    const int tamanhoSolicitado = 4096;

    byte[] buffer =
        ArrayPool<byte>.Shared.Rent(tamanhoSolicitado);

    try
    {
        int lidos = await origem.ReadAsync(
            buffer.AsMemory(0, tamanhoSolicitado),
            cancellationToken);

        // Processar os primeiros "lidos" bytes aqui,
        // enquanto o buffer ainda pertence a esta operação.

        return lidos;
    }
    finally
    {
        ArrayPool<byte>.Shared.Return(buffer);
    }
}
```

Pontos que merecem atenção:

- O array alugado pode ser maior que o tamanho solicitado.
- Seu conteúdo anterior não deve ser considerado inicializado.
- Só os bytes efetivamente lidos devem ser tratados como entrada válida.
- O buffer não deve ser devolvido enquanto uma operação ainda o utiliza.
- Depois da devolução, nenhuma referência ou visão deve continuar sendo usada.
- Dados sensíveis podem exigir limpeza antes da reutilização.

**Pooling troca parte do custo de alocação por responsabilidades adicionais de ciclo de vida.**

### Exercício recomendado

Implemente um parser simples de uma linha como:

```text
produto=42;quantidade=7;preco=19.90
```

Faça duas versões:

1. Com `Split` e strings intermediárias.
2. Com `ReadOnlySpan<char>` e recortes.

Antes de medir desempenho, garanta a equivalência funcional:

- O que acontece quando falta um campo?
- Qual cultura numérica é utilizada?
- Espaços são permitidos?
- Valores inválidos retornam erro ou lançam exceção?
- Campos repetidos são aceitos?

Uma versão mais rápida que trata entradas de maneira diferente não é uma substituição equivalente.

## 3. *Writing High-Performance .NET Code*: transformar conhecimento em decisões de engenharia

**Autor:** Ben Watson.  
**Referência:** [site oficial do livro](https://www.writinghighperf.net/).

### Como ele complementa o livro de memória?

Enquanto *Pro .NET Memory Management* aprofunda o gerenciamento de memória, o livro de Ben Watson oferece uma perspectiva mais ampla de **medição, funcionamento do CLR e otimização de aplicações**.

A leitura ajuda a mudar a pergunta de:

> “Qual construção de C# é mais rápida?”

para:

> “Qual parte do sistema limita a métrica que preciso melhorar?”

### 3.1. Estabelecer uma meta mensurável

“Melhorar performance” é um objetivo incompleto.

Exemplos mais úteis:

- Reduzir a latência p99 de determinado endpoint.
- Aumentar o throughput sem ampliar o número de instâncias.
- Diminuir o uso de CPU mantendo a mesma carga.
- Reduzir memória retida durante um processamento em lote.
- Melhorar o tempo de inicialização.

Esses objetivos podem entrar em conflito.

Por exemplo:

- Um cache pode reduzir latência, mas aumentar memória.
- Mais paralelismo pode reduzir o tempo de um lote, mas elevar consumo de CPU e contenção.
- Um pool pode reduzir alocações, mas manter buffers grandes residentes.

### 3.2. Separar custo local de impacto global

Suponha que um trecho represente 5% do tempo de uma operação.

Mesmo que ele passe a executar duas vezes mais rápido, a operação completa não ficará duas vezes mais rápida.

Em um modelo simplificado:

\[
T_{\text{novo}} = 0{,}95T + \frac{0{,}05T}{2}
= 0{,}975T
\]

A redução do tempo total será de apenas **2,5%**.

Essa é uma aplicação da lei de Amdahl: o ganho total é limitado pela parcela efetivamente melhorada.

**Lição prática:** priorize o custo dominante antes de investir em micro-otimizações.

### 3.3. Ler recomendações considerando a versão do runtime

Livros preservam princípios importantes, mas detalhes de implementação envelhecem.

Ao encontrar uma recomendação específica, pergunte:

- Ela foi medida em qual versão do .NET?
- O compilador JIT atual já realiza essa otimização?
- Existe uma API mais recente?
- O resultado se mantém em ARM64 e x64?
- A recomendação depende de determinado tamanho de entrada?

Use o livro como base de raciocínio, não como uma lista de regras imutáveis.

### Exercício recomendado

Escolha uma operação real e escreva, antes de alterar o código:

1. **Problema:** qual métrica está inadequada?
2. **Evidência:** quais medições demonstram isso?
3. **Hipótese:** qual mecanismo explica o custo?
4. **Intervenção:** qual mudança testa essa hipótese?
5. **Critério de sucesso:** qual melhoria justificaria adotar a mudança?
6. **Risco:** o que pode piorar?

Esse registro evita confundir preferência de estilo com otimização.

## 4. Blog do .NET: acompanhar o que o runtime já otimiza

**Leitura de referência:** [*Performance Improvements in .NET 8*, de Stephen Toub](https://devblogs.microsoft.com/dotnet/performance-improvements-in-net-8).

Os artigos dessa série são úteis porque conectam:

- Exemplos pequenos.
- Benchmarks.
- Mudanças no runtime e nas bibliotecas.
- Explicações sobre os mecanismos responsáveis pelos ganhos.
- Links para alterações no código-fonte.

### 4.1. O que procurar nesses artigos?

#### JIT e código gerado

Estude exemplos de:

- Inlining.
- Desvirtualização.
- Eliminação de verificações redundantes.
- Otimização de loops.
- Vetorização.
- Otimização guiada por perfil, como Dynamic PGO.

A finalidade não é decorar instruções de assembly. É entender por que duas formas aparentemente semelhantes podem produzir resultados diferentes — e por que isso pode mudar entre versões.

#### Bibliotecas e APIs

Observe melhorias em:

- Strings e busca em texto.
- Coleções.
- LINQ.
- Serialização.
- Operações de entrada e saída.
- Parsing e formatação.

Às vezes, o melhor ganho vem de **atualizar o runtime ou adotar uma API existente**, em vez de manter uma implementação manual complexa.

### 4.2. Como interpretar os números?

Não leia “X vezes mais rápido” como uma promessa para qualquer aplicação.

Verifique:

1. Qual operação foi medida?
2. Qual era o tamanho da entrada?
3. Quais versões foram comparadas?
4. Qual arquitetura de hardware foi usada?
5. A medição considera inicialização ou execução estabilizada?
6. Seu sistema realiza essa operação com frequência relevante?

Um ganho expressivo em uma busca específica pode ter impacto mínimo em um serviço cujo tempo é dominado pelo banco de dados.

### Exercício recomendado

Selecione um benchmark de uma API usada no seu projeto e reproduza-o:

- Nas versões de runtime relevantes.
- Com diferentes tamanhos de entrada.
- Com dados semelhantes aos reais.

Depois, valide o resultado na aplicação. O microbenchmark explica um mecanismo; o teste integrado mostra sua relevância.

## 5. Complemento essencial: documentação do BenchmarkDotNet

Para aproveitar as outras leituras, é necessário medir de forma confiável.

**Referências:**

- [Primeiros passos](https://benchmarkdotnet.org/articles/guides/getting-started.html).
- [Boas práticas](https://benchmarkdotnet.org/articles/guides/good-practices.html).

### O que estudar primeiro?

- `[Benchmark]`: identifica o método medido.
- `Baseline`: define a referência de comparação.
- `[Params]`: permite variar entradas.
- `[MemoryDiagnoser]`: adiciona diagnóstico de alocações gerenciadas.
- Aquecimento e repetições.
- Variabilidade dos resultados.
- Execução em `Release`, sem depurador anexado.

### Exemplo didático

O exemplo abaixo é independente do vídeo:

```csharp
using System.Globalization;
using BenchmarkDotNet.Attributes;
using BenchmarkDotNet.Running;

BenchmarkRunner.Run<ParsingBenchmarks>();

[MemoryDiagnoser]
public class ParsingBenchmarks
{
    private const string Entrada = "pedido:12345";
    private const int InicioNumero = 7;

    [Benchmark(Baseline = true)]
    public int ComSubstring()
    {
        return int.Parse(
            Entrada.Substring(InicioNumero),
            CultureInfo.InvariantCulture);
    }

    [Benchmark]
    public int ComSpan()
    {
        return int.Parse(
            Entrada.AsSpan(InicioNumero),
            CultureInfo.InvariantCulture);
    }
}
```

Execute em um projeto de console com o pacote instalado:

```bash
dotnet add package BenchmarkDotNet
dotnet run -c Release
```

### Como ler o resultado?

| Coluna | Interpretação |
|---|---|
| `Mean` | Tempo médio medido por operação |
| `Error` | Margem estatística reportada para a estimativa |
| `StdDev` | Dispersão dos tempos medidos |
| `Ratio` | Relação com o benchmark de referência |
| `Allocated` | Bytes gerenciados alocados por operação no escopo medido |

A hipótese é que a versão com span elimine a string intermediária. **O ganho de tempo precisa ser medido, não presumido.**

Além disso, `Allocated = 0 B` não significa que a aplicação inteira não usa memória ou não aloca. O resultado se refere ao escopo medido e não representa todos os possíveis custos, como memória nativa ou inicialização fora da medição.

Para aprofundar a metodologia, o próprio projeto recomenda **_Pro .NET Benchmarking_, de Andrey Akinshin**, na [documentação do BenchmarkDotNet](https://benchmarkdotnet.org/).

### Como consolidar o aprendizado

Para cada técnica estudada, produza três resultados:

1. **Uma explicação:** qual custo ela pretende reduzir?
2. **Um experimento:** em quais condições a melhoria aparece?
3. **Uma limitação:** quando ela não deve ser aplicada?

Exemplo:

> **Técnica:** reutilizar arrays com `ArrayPool<T>`.  
> **Benefício esperado:** reduzir alocações recorrentes de buffers.  
> **Experimento:** comparar alocação direta e reutilização sob uma carga representativa.  
> **Limitações:** buffers retidos pelo pool, custo de limpeza, complexidade de propriedade e risco de uso após devolução.
